## 2. 工程输入与适用范围

字段核对依据：[任务表](../lib/database/task_tables.dart)、[数据库操作与 priority 说明](../lib/database/app_database.dart)、[表单载体](../lib/models/task.dart)、[EST 转换](../lib/database/task_extensions.dart)。

| 输入 | 当前含义 | v1 处理 |
| --- | --- | --- |
| `priority` | 整数：0 无、1 低、2 中、3 高；0 同时是默认值 | 基础重要性代理；0 不等同于用户明确认定“无价值”，理由需提示“未设置”。 |
| `ddl` | 持久层非空截止时间；表单可在保存前为空 | 计算剩余时间；缺失或无法解析的数据按第 3 节降级。 |
| `status` | 0 未完成、1 已完成、2 已规划、-1 已冻结 | 仅 0、2 进入候选队列，权重相同。1、-1 不参与，不能以零分混入队尾。未知状态返回输入错误。 |
| `now` | 本次计算传入的时钟快照 | 同批任务使用同一 UTC 时间，不能每条各取一次当前时间。 |
| `id` | 已有任务标识 | 仅作同分稳定排序，不代表创建时间。 |

当前还存在可空 `estHour` / `estMinute` 与 `TaskDraft.est: TimeOfDay?`，可表达预计耗时的录入值，**不是实际耗时记录**。v1 不依赖 EST：其时长语义、超过 24 小时表示、缺失率与有效值规则需先统一。当前确定可用于基线的仍是 priority、status、ddl。标题、描述、标签虽存在，尚无可校准的重要性或任务类型标注，不作为评分因子。

## 3. 可直接实现的 v1 计算规则

### 3.1 校验与基础分

先验证 `priority` 是 0–3 的整数、`status` 属于上述四值、`now` 是有效时间；否则返回 `invalid_input`，分数与等级均为 `null`，不进入推荐排序。已完成或冻结任务返回 `excluded`，分数与等级也为 `null`。

对候选任务，以查表方式计算归一化基础值：

| 手动 priority | 基础值 B | 基础贡献 100 × 0.625 × B |
| --- | --- | --- |
| 0（无 / 未设置） | 0 | 0 |
| 1（低） | 1/3 | 20.833333… |
| 2（中） | 2/3 | 41.666666… |
| 3（高） | 1 | 62.5 |

即 `B=priority/3`。将序数等距映射是项目取舍，不表示中优先级的真实效用恰好是高优先级的 2/3。

### 3.2 时间紧急度

把 `ddl`、`now` 转换为 UTC 瞬时，按精确秒差计算剩余小时，不截断到整数小时：

```text
h = (ddl_utc - now_utc).totalSeconds / 3600
U = 1 / (1 + max(h, 0) / 24)
```

`U` 在 (0,1]；截止瞬间及已逾期均为 1，没有除零或负优先级。例：剩余 72h、24h、6h、0h 对应 0.25、0.5、0.8、1。逾期时另输出逾期标记与逾期小时，分数不随逾期时长无限膨胀。

**24h 时间常数**是日常计划的初始尺度：距截止一天时获得一半紧急度；未来应通过反馈校准。它不是材料给出的实验最优值，也不是“剩一天才开始”的建议。

缺失 / 无效 `ddl` 时令 `U=0`，保留 0.625 / 0.375 权重，输出 `missing_deadline` / `invalid_deadline` 警告，不能临时把基础权重提为 1。持久层正常任务不应缺失，降级用于未保存草稿或导入异常。无时区的旧时间按应用当前本地时区解释并在理由中记录该时区；后续应规范存储时区。只有日期的输入须在录入边界明确转换为该本地日期的日末时刻，不能在评分层自行猜测；夏令时按时区转换后的真实时差计算。

### 3.3 总分与等级

```text
S = 100 × (0.625 × B + 0.375 × U)
```

`S` 范围为 [0,100]。先用未舍入的 S 判断等级与排序，仅展示时四舍五入到两位小数；理由中的贡献也仅在展示时舍入。

| 未舍入分数 | 建议等级 | 应用含义 |
| --- | --- | --- |
| 70 ≤ S ≤ 100 | A：优先关注 | 优先评估是否现在执行，仍需用户确认资源与情境。 |
| 40 ≤ S < 70 | B：近期安排 | 进入近期计划，兼顾重要但不紧急的任务。 |
| 0 ≤ S < 40 | C：计划处理 | 纳入后续计划；不代表可丢弃，仍显示截止提醒。 |

**阈值理由（项目冷启动规则）**：仅时间因素最多贡献 37.5，低于 40，避免未设置重要性的临期任务占满最高档；中重要性即使无截止也有 41.666…，高重要性至少 62.5，均能进入近期安排，保护长程目标。高重要性达到 A 需要 `U≥0.2`，即剩余不超过 96h；中重要性需 `U≥34/45≈0.755556`，即剩余不超过 `132/17≈7.764706h`。因此 A 要求重要性与紧急度共同支持。低重要性即使逾期最高也只有 58.333…，不会成为 A；这是已知取舍，界面仍须显示逾期提示，并允许用户重新评估手动重要性。分档不是截止提醒的开关。

三档是对 [R] §3.1 的呈现建议作的适配；不把 A/B/C 写回数据库 `priority` 的 0–3，也不把研究中的“资源缺失则稍候”规则伪装成已实现的判断。

### 3.4 排序、重算与稳定性

候选任务按以下键排序：未舍入 S 降序、有效 ddl 升序（缺失 / 无效置最后）、id 数值升序。草稿没有 id 时用调用方提供的稳定输入序号补齐最终平局。相同输入、now、算法版本应产生相同结果；不按列表内最大最小值归一化，新增任务不改变旧任务分数。

在创建 / 修改 priority、ddl、status，完成 / 冻结 / 恢复，打开或恢复应用时重算；应用前台可每 60 秒刷新一次，实际接入时以调度器为准，恢复时立即补算，不要求后台常驻。时间推进只更新 U，不冒充从历史学习；同一次刷新批量替换排序快照。专注会话中可更新建议，但不自动抢占用户当前任务（[R] §1.3.1 的切换成本、§4.1 的承诺与心流；[E] §2.1 Liminal）。

## 4. 输出契约与应用

以下是未来实现的结果契约，不要求本次增加字段或代码：

```text
algorithm_version: cardo-v1
calculated_at: 本批 now 的 UTC 时间
eligibility: eligible | excluded | invalid_input
score: 未舍入 S，或 null
level: A | B | C，或 null
factors: { B, U, base_contribution, urgency_contribution }
reasons: 手动档位、剩余/逾期小时、两项贡献、等级解释
warnings: 未设置重要性、截止时间缺失/异常、旧时间解释时区等
```

只对 eligible 产生 factors；其他情况返回排除 / 校验原因。贡献以分为单位，二者之和等于 S。理由不能写“因为历史效率高”或“阻塞下游任务”，因为当前未计算这些因子。

Prospect 可按分数排序、按等级分组；卡片显示等级与一条关键理由，详情显示贡献分解。手动 priority 保持用户意图输入，算法分数作为派生建议；用户调整输入后重算，不静默覆盖。Review 后续收集推荐接受与修正记录，为校准提供证据。v1 不执行任务、不承诺可行排程、不根据分数自动完成或冻结任务。

## 5. 带具体数字的算例与边界

以下同批 `now=2026-11-08T12:00:00Z`，任务均为 status=0（除明确注明外）。

| 例 | 输入 priority / ddl | 归一化 B / U | 基础贡献 + 时间贡献 = S | 输出 |
| --- | --- | --- | --- | --- |
| 1：重要且临期 | 3 / `2026-11-08T18:00:00Z`（6h） | 1 / 0.8 | 62.5 + 30 = **92.5** | **A**；“手动高，剩余 6h；重要性 62.50 分、紧急度 30.00 分。” |
| 2：中等且远期 | 2 / `2026-11-11T12:00:00Z`（72h） | 2/3 / 0.25 | 41.666666… + 9.375 = **51.041666…** | **B**，展示 51.04；“手动中，剩余 72h，建议近期安排。” |
| 3：未设置且逾期 | 0 / `2026-11-08T06:00:00Z`（-6h） | 0 / 1 | 0 + 37.5 = **37.5** | **C**；同时提示“逾期 6h、重要性未设置，请复核”，不能隐藏逾期。 |
| 4：长程重要、无截止的降级输入 | 3 / 缺失 | 1 / 0 | 62.5 + 0 = **62.5** | **B**，`missing_deadline`。 |
| 5：同例 1 但已完成 | 3 / 同例 1，status=1 | 不计算 | `score=null` | `excluded`、`level=null`，移出推荐。 |

可供后续实现验收的数值边界：priority=3、剩余 96h 时恰好 70→A；priority=1、剩余 `528/23≈22.956522h` 时恰好 40→B；截止瞬间 U=1；任意逾期 U=1；分数 69.999 即使展示成 70.00 仍为 B，展示应保留等级并可在详情查看更多精度。status=2 与 0 的评分相同，-1 排除；priority=4 返回 invalid_input。上述验收项是文档中的实现约束，本次未新增测试或算法实现。

## 6. 数据缺口与后续扩展

以下因子应在完整模型中考虑，当前不能据此评分。未知数据不应伪造成零效率、零成本或“无依赖”；也不能新增一个因子却沿用旧版本权重和阈值。

| 理论因子 / 来源 | 当前不足 | 需要补齐的数据与后续计算方向 |
| --- | --- | --- |
| 等待老化、防饥饿、任务衰减；[E] §2.1–2.2 | 无创建时间与衰减参数，不能用 id 推断年龄 | `created_at`、价值复核时间、任务类型 / 衰减参数。可用 `A=min(age_days/30,1)` 表示等待提升；价值衰减可用 `V(t)=V0×exp(-λt)`。两者方向相反，须按任务类型验证，30 天与 λ 都待校准，不能统称时间紧急度。 |
| DAG、关键前置、阻塞传播；[R] §2.1.2、§3.1、§4.3.4；[E] §2.1 | 无依赖边、前置完成关系 | `predecessor_ids` 或依赖边表、边类型；校验环路。先过滤前置未完成任务，再评价解锁下游收益；缺图不能声称已满足依赖。 |
| 耗时、价值密度、可用时间匹配；[R] 摘要、§1.1.2、§4.3.1 | 有可空 EST，但时间对象与时长语义未统一，无剩余工作量及日历时间块 | 统一 `estimated_duration_minutes`、已投入时长 / 剩余估计、`available_minutes`。候选短任务因子可为 `Q=1/(1+estimated_minutes/60)`；须限制短任务偏好并保护长程任务，60 分钟只是待验证尺度。 |
| 历史专注效率、完成转化与预测误差；[E] §2.1–2.2；[R] §4.3.2 | 无实际耗时、专注区间、完成时间；status 快照无法推导速率 | `focus_sessions(task_id,start,end,interruptions)`、`completed_at`（对应蓝图 crossed_at）、实际有效分钟与估计历史。才能比较预计 / 实际耗时及分时段效率；冷启动保持禁用。 |
| 稳定性、失败退避；[R] §4.3.1–4.3.2 | 无尝试次数、成功 / 失败与原因历史 | `attempts`、`outcome`、`failure_reason`、事件时间。可用 `(successes+1)/(attempts+2)` 平滑成功率，但须区分人工作业与工具失败，不能因困难自动贬低重要任务。 |
| 环境、资源、用户状态；[R] §1.1.1、§2.2、§3.1 | 无工具就绪、精力 / 压力、可用连续时间等输入；tags 不等于这些标签 | 先以可选简明问题收集 `resources_ready`、时间块、用户自述精力及任务需求；资源不可用应作为执行门槛。传感器推断与多智能体负载属于后续场景，不能套用机器人或 CPU 指标代替个人状态。 |
| 目标影响、偏好与反馈校准；[R] §1.3、§3.1、§4.3.3 | priority 混合主观判断，0 还可能为默认值；无目标关联与推荐反馈 | 目标关联 / 影响度、是否显式设置 priority、推荐曝光 / 接受 / 改档 / 忽略及时间、算法版本。先用简明问答区分重要性、紧急性与资源，再学习个人权重。 |

扩展评分框架为 `S=100×Σ(w_j×f_j)`，要求各 `f_j∈[0,1]`、`w_j≥0`、`Σw_j=1`；每个新因子必须声明单位、方向、缺失策略与理由。硬门槛（完成、冻结、依赖未满足、资源不可用）先处理，不靠加减分代替。v1 固定只启用 B、U，不预留有分值却无数据的“环境 20%”。新增模型应提升版本号并重新校准分档，不能把上表示例函数直接当作 v1 已启用规则。

校准顺序：先采集版本化推荐与真实执行反馈，按时间分割离线评估，再小范围验证。比较手动排序、仅截止时间排序与 v1 的逾期率、重要任务完成率、用户改档 / 接受率和排序变动频率，避免只优化短任务吞吐。没有完成时间目前无法计算逾期完成率，没有曝光记录也无法计算接受率。对权重比例、24h 常数、40/70 阈值逐项做敏感性分析；样本不足时维持默认值，不假装已经个性化。记录参数变更、允许恢复默认，并监控无截止、低重要性和长任务是否长期被忽略。强化学习、模糊控制与多目标优化（[R] §5.1）作为数据充分后的选项，当前无训练反馈与可观测环境，不作为首版实现前提。
